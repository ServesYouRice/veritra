<goal>
Make sendPendingAttachments and ComposerAttachments in mobile/lib/features/chat/composer_attachments.dart meet four requirements. Send only items still in the tray. Keep an in-flight item's temporary file until its send finishes. Hold a batch-level send guard for the whole run of one sendPendingAttachments call, including the post-send tray.remove()/discard() awaits and the failure path, so that a second call on the same tray can never send anything while the first call is still running.

This matters because it fixes:
- Attachment removed from the tray during an in-flight send is still sent (medium)
  sendPendingAttachments takes a snapshot of the tray once with `tray.items`, which returns an unmodifiable copy. It then awaits one encrypted send per item. During that loop the AttachmentTray chips keep an active delete action, and remove() takes the item off the live list and deletes temporary copies. The loop never checks whether an item is still in the tray before sending it. A file the user removed mid-send is therefore still encrypted and sent. For a pasted image, the file is deleted underneath the pending send, which then fails or races with the read. The same applies to clear() during a send. Nothing in this file stops sendPendingAttachments from running twice at once, which would send duplicates.
- Removing a queued attachment does not remove it from the send batch (medium)
  Sending iterates a copied list and never checks whether later items remain queued. The tray exposes removal without a sending guard. Unless an omitted caller freezes the tray, removing a later file while an earlier upload is pending only changes the live tray: the removed file is still sent from the snapshot.
</goal>

<context>
- Issue claim to check: 'final items = tray.items;' takes a one-time unmodifiable copy. The loop never re-checks membership, while AttachmentTray keeps 'onDeleted: () => tray.remove(item)' active.
- remove() deletes temporary (pasted) files immediately through discard(), which can race a pending send's read of the file.
- After each successful send the loop runs 'await tray.remove(item);', and remove() runs 'await item.discard();'. That gap, and the gap between iterations, are both points where a second call could enter. A per-item in-flight marker does not cover them (critique PC-070-BATCH-SEND-GUARD). Only a batch-level guard held across the whole loop does.
- ChatScreen._send only checks state.isBusy(Ops.attachment) before starting. The verifier rated the double-send part less certain, so test it.
</context>
