This matters because it fixes:
- DeleteAccountData leaves exported account-owned data (key packages, blocks, mute preferences, call metadata) in place (medium)
  The function documents that it scrubs account-controlled metadata and keeps only pseudonymous IDs. The export enumerates the account-owned categories, but the deletion transaction does not touch four of them: - call_sessions created by the account, including metadata_json and invited_account_id - device_key_packages uploaded by the account's devices (only devices.key_package is blanked) - account_blocks where the account is the blocker - conversation_notification_preferences The accounts and devices rows are updated rather than deleted, so an ON DELETE CASCADE from those tables cannot remove the dependent rows. conversation_notification_preferences might cascade from memberships only if the schema defines such a foreign key, which is not visible in scope.
- Row iteration failures can silently truncate exports and blob cleanup (medium)
  Both loops check Close but never Rows.Err. Next can return false because iteration failed, and Close does not substitute for checking that failure. exportAssociatedData can therefore return a successful, incomplete category. DeleteAccountData can proceed with an incomplete storage-key list if an iteration error leaves the transaction usable.
