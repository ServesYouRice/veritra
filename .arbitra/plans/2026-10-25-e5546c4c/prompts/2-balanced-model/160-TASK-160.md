<goal>
Make rateLimiter.bucketLocked and evictOneLocked never delete an unexpired bucket. When a table is full and nothing has expired, charge the key to a per-table overflow bucket.

This matters because it fixes:
- A full address table evicts live buckets, so an attacker holding one IPv6 /48 can recycle exhausted credential-route budgets (medium)
  rateLimitHost groups IPv6 clients only by /64, and nothing aggregates at a coarser prefix. The address table, which also holds the auth (credential) and enrollment counters, is capped at 65536 entries. When a new key arrives and the table is full, bucketLocked calls evictOneLocked. That function deletes a live, unexpired bucket: the one with the earliest reset among up to 32 entries taken from map iteration. It does not refuse the request or fall back to a shared key. Evicting a bucket throws away its auth and enrollment counts before the minute is up. The struct comment says the tables are split so that evictions cannot 'reset their credential budgets', but the address table itself still allows exactly that. A /48 holds 65536 /64s, so one routed /48 has enough distinct keys to fill the table by itself. Once the table is full, each new attacker key evicts an entry that is probably one of the attacker's own older, exhausted buckets. When the attacker cycles back to that /64, it gets a fresh budget even though its one-minute window has not ended.
</goal>

- section-a4fb67428955705a5ccb12c0/Q-001: When a bounded in-memory table is full and every sampled entry is live, what should happen to a new key? This covers admission.Budget in server/internal/admission/admission.go (maxBudgetEntries) and rateLimiter.buckets/accountBuckets in server/internal/app/app.go (maxRateLimitEntries). The options are: (a) admit through one shared overflow bucket per table with the same per-window limits; (b) refuse the new key with 429/Retry-After; (c) let the table grow past the cap. Option (a) is planned as the default because it keeps both the memory bound and the invariant stated in the rateLimiter struct comment that evictions must not reset credential budgets. The cost is that new legitimate keys share one budget during a flood. Maintainers may prefer (b) for the admission budget. No measurement shows which option is better for availability.
</open_questions>
