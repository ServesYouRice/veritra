<goal>
Make the AppState device-link tests able to tell a locally derived SAS from a server-supplied one, and prove that the claiming device rejects mismatched transcript, nonce or account data.

This matters because it fixes:
- Claiming-device transcript binding is not exercised and fake server checks are permissive (medium)
  On the claimer side, the fakes accept anything: - completeDeviceLinkClaim ignores expectedTranscriptHash and always returns a session. - claimDeviceLink ignores the DeviceLinkVerification argument. - approveDeviceLink checks only the hash length and its first byte. The fail-closed mutation loop (lines 288-314) covers only the owner's refresh path. No test makes the claiming device reject a mismatched transcript, nonce or account. The test 'app state drives device link claim through approval' never performs or checks an approval.
- Device-link SAS tests cannot tell a locally derived code from a server-supplied one (medium)
  FakeDeviceLinkApiClient._link builds DeviceLink objects directly, bypassing fromJson, which the suite shows discards server codes. It sets verificationCode to '65432101' for every non-pending link. That is the same value the tests expect to be displayed and the value the user types to approve. So the refresh assertions (lines 249, 272, 301) and the claimer assertion (line 176) pass whether AppState derives the SAS from the verified transcript or passes through the server-provided field. Only the create and approve responses are tested with a dishonest server code.
</goal>
