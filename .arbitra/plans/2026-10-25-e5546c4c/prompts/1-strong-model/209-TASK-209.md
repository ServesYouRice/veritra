<goal>
Add an opt-in bounded sync mode. In this mode ListSyncEvents (server/internal/storage/message_store.go) caps candidate reads per request and reports the id of the last candidate it may safely skip past (scannedThrough) and whether the budget truncated the scan. The syncEvents handler exposes these values as additive fields, next_after_id and scan_truncated. Cursor-expiry validation accepts those positions. The mobile AppState catch-up owner advances its persisted cursor to next_after_id only after a page is fully applied, and keeps paging while scan_truncated is true, so a hidden tail is not rescanned on every poll. Requests without the opt-in keep the current behaviour exactly.

This matters because it fixes:
- ListSyncEvents re-scans the entire run of hidden trailing events on every poll (medium)
  ListSyncEvents reads candidates until it has collected limit visible events or the stream ends. It returns only the visible events and does not report how far it scanned. Some events after the last visible one may all be hidden: events from a blocked sender, pre-join encrypted events, or call events for a device that has not joined. In that case every request walks the whole hidden tail, evaluating the block and MLS predicates (json_extract plus correlated subqueries) on each row, and returns an empty or short page. The client cannot move its cursor past hidden events, because SyncBounds' latest value is also visible-only. Every subsequent poll repeats the full scan.
</goal>

<context>
- Claim to check: ListSyncEvents tracks 'last' but returns only visible events. Neither the handler (which adds epoch, oldest and latest) nor the client can move the cursor past a hidden tail.
- The query has no LIMIT; the caller's early rows.Close ends the merge, so a scan budget can be enforced in the Go loop.
- Critique: the expiry check accepts a cursor only when its row exists and is not blocked for the device, and otherwise compares it with the oldest visible row. A scanned-through id that points at a blocked row would therefore be reported as expired. On the client, expiry leads into sync-recovery paths, so a false expiry is severe.
- Critique: the AppState catch-up loop breaks on an empty page and on a short page, and reloads its cursor from the local store. Cursor persistence and termination live in app_state.dart, not in sync_service.dart. The supplied sync_service.dart holds only the WebSocket transport and AccountSyncEngine.
- Critique: ApiClient.syncEvents returns only the 'events' rows. Legacy clients ignore new fields, so an unconditional budget would strand them on a repeated empty page. The budget is therefore opt-in.
- Other tasks change the AppState catch-up loop (TASK-031 retains committed-but-unpublished envelopes, TASK-032 stall policy, TASK-034 recovery storage errors, TASK-036 projection coalescing). The cursor advance must not skip anything those policies leave unapplied.
</context>
