<goal>
Ensure the MLS credential SignatureKeyPair never signs caller-chosen bytes without a fixed domain-separation prefix, and that the server enrollment verifier matches.

This matters because it fixes:
- sign_enrollment_challenge signs raw caller bytes with the MLS identity key, creating a cross-protocol signing oracle (high)
  The public method `MlsDevice::sign_enrollment_challenge` passes the challenge straight to the same Ed25519 `SignatureKeyPair` that signs this device's MLS LeafNode, KeyPackage and FramedContent structures. The only check is that the challenge is non-empty. The doc comment puts domain separation on the server, but elsewhere the module treats the server as untrusted. OpenMLS produces MLS signatures by serializing `SignContent` (a varint-length-prefixed label "MLS 1.0 <Label>" followed by the content) and signing those bytes with pure Ed25519. Whoever controls the challenge can therefore get a valid MLS signature over any MLS structure they choose. `create_enrollment_credential` adds a prefix, so it is safe, but the raw signer stays public, and the tests call it directly with an arbitrary challenge.
</goal>

<context>
- Claim to check: `pub fn sign_enrollment_challenge` checks only `challenge.is_empty()` before `self.signer.sign(challenge)`.
- create_enrollment_credential already prefixes with b'veritra-enrollment-proof-v1'.
- RFC 9420 section 5.1.2 SignWithLabel signs SignContent: a varint-length label 'MLS 1.0 ' + Label, followed by the content. A fixed ASCII prefix such as 'veritra-...' starts with byte 0x76. Read as an RFC 9420 varint, that is a 2-byte length, so bytes 2 onward would have to be 'MLS 1.0 ', but they are 'ritra-'. A prefixed message therefore cannot parse as a SignContent.
</context>
