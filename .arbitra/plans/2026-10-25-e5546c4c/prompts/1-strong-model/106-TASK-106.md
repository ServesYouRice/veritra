<goal>
First confirm the claim that received and own-echo message expiry is copied from the unauthenticated server envelope. After section-26579cea45f35cfc5617fb36/UQ-1 is decided, make the client derive or bound expiry from the chosen authenticated source, and add tests that a forged expiry cannot drop history.

This matters because it fixes:
- Message expiry appears to come from server-stamped envelope metadata; the first own echo is trusted without bounds (medium)
  The tests describe a design in which the server stamps expiry and the client adopts it: - The receive helper, documented as doing what the native service does, copies the envelope's expiresAt into the stored message. - The sender's local copy learns its expiry from the server echo. - Only the first echo is honoured; later echoes cannot move or shorten it. The test at line 338 states that server listings are not authenticated. No test shows the stamped expiry being checked against an authenticated value, such as a timer carried in the MLS plaintext or group context, or bounded below by createdAt plus the conversation's configured timer. A server can therefore choose a past or near-immediate expiry on the first echo and delete the sender's own copy. For received messages, a past expiry means the message is consumed (MLS state and cursor advance) but never stored. Messages a server can shorten this way contradict the property tested at line 332, that a server cannot erase history.
</goal>
